CORE CONCEPTS
================================================================================

1. DEVICE-SPECIFIC JID FORMAT
   Standard: "1234567890@s.whatsapp.net" (all devices)
   Device-specific: "1234567890:0@s.whatsapp.net" (device 0)
   Device ID 0 = primary device
   Device ID 1+ = secondary devices (desktop, web)

2. SILENT PING TYPES (11 total)
   - Reaction: Empty reaction to non-existent message
   - Delete: REVOKE protocol (type 0) for message deletion
   - Edit: MESSAGE_EDIT protocol (type 14)
   - Call-Reject: CALL_LOG_MESSAGE (type 22) with call outcome
   - Unknown: Non-existent protocol (type 101)
   - Poll Response: Vote on non-existent poll
   - Button Response: Button interaction with fake ID
   - Device Coordination: Multi-device sync message
   - App State: Fatal exception notification
   - Peer Data: P2P data operation request
   - Malformed: Invalid proto field for validation testing

3. FINGERPRINTING LOGIC
   Primary Device (ID=0):
   - Reaction success + Delete timeout = Android
   - Reaction success + Delete success = iOS
   
   Secondary Device (ID>0):
   - Call-reject timeout = Desktop
   - Call-reject success = Browser

4. MESSAGE STATUS CODES
   0: failed
   1: sent (to server)
   2: ack (protocol-level)
   3: delivered (to device)
   4-5: read (by user)

5. DEVICE TARGETING
   Uses relayMessage() with participant option:
   await socket.relayMessage(jid, message, {
     messageId: id,
     participant: {
       jid: "user:deviceId@s.whatsapp.net",
       count: 0
     }
   })

IMPLEMENTATION FLOW
================================================================================

GET DEVICES:
  Frontend (Get Devices button)
    ↓ ApiService.getDevices(user)
    ↓ GET /api/devices/:user
    ↓ WhatsAppService.getDevices()
    ↓ socket.getUSyncDevices([jid], false, false)
    ↓ Returns DeviceInfo[] {user, device}

SEND SILENT PING:
  Frontend (Click Ping Button)
    ↓ ApiService.silentPing({user, deviceId, type})
    ↓ POST /api/devices/ping
    ↓ WhatsAppService.silentPing()
      1. Generate two messageIds (target + actual)
      2. Create type-specific message content
      3. Set 30-second timeout
      4. Track in pendingSilentPings map
      5. Call relayMessage with device-specific JID
    ↓ WhatsApp server processes
    ↓ messages.update event received
    ↓ handleMessagesUpdate() checks pendingSilentPings
    ↓ Emit 'ping.result' via WebSocket
    ↓ Frontend socket listener updates UI state
    ↓ Display status (online/offline/timeout)

PROFILE ALL:
  Step 1: Register event handler BEFORE sending (avoid race)
  Step 2: Send reaction pings to all devices (staggered 200ms)
  Step 3: Monitor responses in real-time
  Step 4: Auto-fingerprint online devices
    - Primary: send delete ping for OS detection
    - Secondary: send call-reject ping for type detection
  Step 5: Timeout after 35s or all devices processed

================================================================================
CRITICAL IMPLEMENTATION DETAILS
================================================================================

1. DEVICE-SPECIFIC DELIVERY
   - Uses WhatsApp's native ":deviceId" JID extension
   - Passed via participant.jid option to relayMessage()
   - Server-side translation to proper binary format

2. MESSAGE TRACKING
   - Each ping gets unique actualMessageId for tracking
   - Targets non-existent message via randomMessageId
   - 30-second timeout per ping
   - Cleanup on ACK for delete pings, delivered/read for others

3. RECEIPT HANDLING
   - Messages.update event provides status codes (0-5)
   - Delete pings: cleanup on status >= 2 (ACK is final)
   - Other pings: cleanup on status >= 3 (need delivery proof)
   - Round-trip time calculated from timestamp difference

4. EVENT FLOW
   - Backend: WhatsAppService extends EventEmitter
   - Emits 'ping.result' with SilentPingResult object
   - Frontend: socket.on('ping.result', handler)
   - WebSocket bridge in socket.ts relays events

5. BATCH OPERATIONS
   - Event handler MUST be registered before pinging
   - Staggered delays prevent system overload
   - 35-second timeout for completion
   - Progress tracking every 2 seconds
